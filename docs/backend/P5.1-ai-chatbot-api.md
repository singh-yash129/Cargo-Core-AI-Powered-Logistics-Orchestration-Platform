# Phase 5.1 — AI Chatbot API (Gemini SQL Writer)

> **Status:** In Progress  
> **Created:** 2026-02-25  
> **Owner:** QuadCore Devs

---

## Overview

Build a multi-turn AI chatbot API that uses **Google Gemini's function-calling** with a
dynamic SQL writer. When the user asks a data-related question, Gemini writes a `SELECT`
SQL query; the backend **validates it** (whitelist `SELECT` only, block mutations), **executes
it on a read-only DB session**, feeds the results back to Gemini, and Gemini composes a
human-friendly answer. For general questions (greetings, advice, logistics knowledge),
Gemini responds directly without touching the database.

Conversations are persisted in an `ai_conversations` table for multi-turn context.

## Architecture

```
User Message
    │
    ▼
┌──────────────┐
│  POST /chat  │  (FastAPI Router — thin)
└──────┬───────┘
       │
       ▼
┌──────────────┐     ┌────────────────────┐
│  AI Service  │────▶│  Gemini 2.0 Flash  │
│  (orchestr.) │◀────│  (function-calling) │
└──────┬───────┘     └────────────────────┘
       │                      │
       │         ┌────────────┘
       │         │ returns execute_sql_query(sql)
       │         ▼
       │  ┌──────────────┐
       │  │ SQL Validator │  parse → whitelist SELECT → block sensitive cols
       │  └──────┬───────┘  → enforce table whitelist → inject LIMIT
       │         │
       │         ▼
       │  ┌─────────────────────┐
       │  │ Read-Only DB Session │  PostgreSQL: SET TRANSACTION READ ONLY
       │  └──────┬──────────────┘
       │         │ results
       │         ▼
       │  Feed results back to Gemini → natural language answer
       │
       ▼
┌──────────────────────┐
│ ai_conversations (RW)│  persist user msg + assistant response + metadata
└──────────────────────┘
```

### Defense in Depth (4 layers)

| Layer | What it catches | Bypassable? |
|-------|----------------|-------------|
| **Gemini system prompt** | Instructs AI to only write SELECTs | Yes (prompt injection) |
| **`sqlparse` validator** | Deterministic — blocks non-SELECT, DDL, DML | Possible edge cases |
| **`password_hash` column filter** | Strips sensitive columns from queries | Possible edge cases |
| **PostgreSQL read-only transaction** | DB engine rejects any write op | **No** (engine-enforced) |

## Tech Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| LLM | Google Gemini 2.0 Flash | Already configured (`gemini_api_key`), fast, cheap, native function-calling |
| SQL generation | AI-generated via function-calling | Flexible — handles any query pattern. No pre-coded SQL templates to maintain |
| SQL safety | `sqlparse` + read-only DB session | Deterministic validation + database-level enforcement |
| Conversation storage | PostgreSQL `ai_conversations` table | Persistent, queryable, supports analytics |
| Framework | None (direct Gemini SDK) | Lean, no LangChain/Vanna dependency churn. ~300 LoC |
| Why not Chat2DB | Java standalone app, not embeddable in Python | |
| Why not LangChain | Heavy framework (~100 deps), sync SQL, frequent API breaks | |
| Why not Vanna.ai | v2.0 too new (Feb 2026), worth revisiting in 3-6 months | |

### Step 5 — SQL Validator

**File:** `backend/app/services/sql_validator.py`

`validate_sql(sql: str) → str` — the gate between Gemini and the database:

1. Parse with `sqlparse` to get statement type
2. **Whitelist:** Only `SELECT` allowed — reject `INSERT`, `UPDATE`, `DELETE`, `DROP`, `ALTER`, `TRUNCATE`, `CREATE`, `GRANT`, `EXECUTE`, `COPY`, `DO`
3. **Block dangerous patterns:** `INTO`, `pg_` system catalogs, `pg_sleep()`, `lo_export()`, `COPY TO`, `DO $$`
4. **Table whitelist:** Only `users` and `roles` (expandable). Parse table references and reject unknown tables
5. **Column blacklist:** Block `password_hash` — never expose it
6. **Row limit:** Inject `LIMIT 50` if not present
7. Return sanitized SQL or raise `ValueError`

### Step 8 — AI Service layer (core)

**File:** `backend/app/services/ai_service.py`

**`async chat(db, ro_db, user, session_id, message)`** — main orchestration:

1. Generate new `session_id` if None
2. Load last N messages from `ai_conversations` for context
3. Build system prompt with:
   - Assistant persona + behavior rules
   - Full DB schema as DDL (CREATE TABLE for `roles`, `users`)
   - Seed data for roles (valid role names)
   - Rules: "Only write SELECTs. Never query `password_hash`. Use PostgreSQL syntax."
   - Current user context: `{name}, role {role}`
4. Call `model.generate_content()` with tools
5. **If function call returned:**
   - Extract `sql_query` → validate via `sql_validator` → execute on `ro_db`
   - Feed results back to Gemini → get natural language answer
   - Persist with `intent="db_query"`, `sql_generated=sql`, `query_result=results`
6. **If plain text returned:**
   - Persist with `intent="general"`
7. Return `ChatResponse`

**`async get_conversation_history(db, session_id, user_id)`**  
**`async get_user_sessions(db, user_id)`**

## Future Expansion

- **Phase 2+ tables:** When orders, inventory, fleet tables are added, update the schema DDL in the system prompt and add tables to the validator whitelist. No code changes to the orchestration layer.
- **WebSocket streaming (Phase 7):** `WS /api/v1/ws/ai-chat/{session_id}` for streaming responses. Service layer stays the same.
- **Vanna.ai migration:** If Vanna.ai v2 stabilizes, can swap the SQL generation layer behind the service interface without touching router/schema layers.
- **Escalation (Phase 5.1):** Add `escalations` table and endpoints for handing off to human agents.
