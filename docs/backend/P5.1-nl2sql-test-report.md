### Latency Breakdown (DB queries)

The ~4.5s average for DB queries is composed of:
1. **Gemini call #1** (~2-3s): Generate SQL from natural language
2. **SQL validation** (~0.1ms): sqlparse parsing + whitelist checks
3. **PostgreSQL execution** (~1-5ms): Read-only query on local DB
4. **Gemini call #2** (~2-3s): Interpret results and format response

> The bottleneck is 100% Gemini API latency. Database and validation times are negligible.

### Recommendations for Production

| Strategy | Expected Impact |
|----------|----------------|
| Gemini 2.5 Flash achieves ~2-3s per call on free tier | Upgrade to paid tier for lower latency |
| Cache frequent queries (e.g., "total users") with Redis | Eliminate Gemini calls entirely for repeated questions |
| Streaming responses (`stream=True`) | Perceived latency drops to <1s for first tokens |
| Batch the 2 Gemini calls into 1 (streaming function execution) | ~50% reduction for DB queries |

## Bugs Found & Fixed During Testing

| Bug | Root Cause | Fix |
|-----|-----------|-----|
| 500 error on percentage queries | `Decimal` type from PostgreSQL not handled by `_make_json_serializable()` | Added `Decimal` → `int`/`float` conversion |
| Unhandled exceptions in router | No top-level try/except in `POST /chat` endpoint | Added safety net returning `ChatResponse(intent="error")` |

## Conclusion

The NL2SQL system is **production-ready for Phase 5.1 scope** (users + roles tables):

- **Accuracy**: 14/14 DB queries returned correct, well-formatted results
- **Security**: 5/5 attack vectors blocked at the LLM level (3 additional defense layers untested but in place)
